# RMA Operations Tracker

A web-based workspace for recording supplier return merchandise authorization (RMA) requests and following each return through to its resolution.

## Why I built it

Supplier returns can become difficult to manage when dates, reference numbers, notes, and follow-ups are spread across different records. I built this tracker with AI assistance to bring those details into one shared workspace and make the status of each return easier to see.

The project combines my experience in customer service, technical support, and returns operations with practical workflow automation. Its goal is to reduce missing details and make daily supplier follow-ups easier.

## What this version does

- Provides access through a shared company code and server-side sessions.
- Creates and updates RMA records stored in SQLite.
- Records supplier/distributor, reference, processing employee, notes, resolution, and ERP status.
- Tracks dates entered, requested, accepted, and returned.
- Shows dashboard counts for active, waiting, returned, and completed RMAs.
- Searches references, suppliers, employees, resolutions, and notes, with a status filter.
- Automatically generates a reference when one is not supplied.
- Records creation and update events in a database history table.
- Adjusts the layout for desktop and mobile screens.

**Scope:** ERP status is entered manually in this version. Automatic OpenERP/Odoo synchronization, email/SMS notifications, and individual user accounts are not implemented in this source. The history table is stored in the database; this version does not display it in the interface.

## Technology

PHP 8.1 or later, PDO SQLite, HTML, CSS, and vanilla JavaScript. No framework or frontend build step is required.

## Run locally

Requirements: PHP 8.1+ with `pdo_sqlite` and `sqlite3` support.

From the project directory:

```bash
php scripts/setup.php --local
php -S 127.0.0.1:8080 -t public
```

Open `http://127.0.0.1:8080` and enter the access code printed by the setup command. The tracker starts empty. Add fictional records when demonstrating it.

The setup command creates a private `config.php` and refuses to overwrite an existing configuration. It generates a random access code and stores only its password hash. The `--local` option permits the session cookie on local HTTP.

## Deploy on PHP hosting

1. Place the project on a host with PHP 8.1+ and PDO SQLite.
2. Run `php scripts/setup.php` without `--local`, or copy `config.example.php` to `config.php` and supply a hash generated by PHP `password_hash()`.
3. Set the website document root to the project's `public` directory and enable HTTPS.
4. Allow the PHP process to write to the configured data directory. Keep that directory and `config.php` outside the public document root.
5. Share the access code only with authorized users.

For deployments managed through environment variables, `RMA_ACCESS_CODE_HASH` overrides the configured password hash and `RMA_DATA_DIR` overrides the data directory. Use an absolute path for the data directory.

GitHub holds the project source; the running application needs PHP hosting.

## Project files

| Path | Purpose |
| --- | --- |
| `public/index.php` | Interface, session access, JSON endpoints, and database setup |
| `config.example.php` | Configuration template containing no credentials |
| `scripts/setup.php` | Generates private configuration and a new access code |
| `config.php` | Local configuration; excluded from Git |
| `var/` | Default runtime database directory; excluded from Git |

## JSON endpoints

Endpoints use `public/index.php?api=...`, or `/?api=...` when `public` is the document root.

| Method | Action | Purpose |
| --- | --- | --- |
| POST | `auth` | Open a session using `{"code":"your-access-code"}` |
| POST | `logout` | Close the current session |
| GET | `rmas` | Read records after authentication |
| POST | `rmas` | Create a record; supplier and processedBy are required |
| PUT | `rmas` | Update a record by its id |

## Portfolio copy

This repository copy excludes the original access-code hash, the embedded supplier return record, and runtime databases. It uses configurable access and starts with no records. Use fictional data for screenshots and demonstrations.

The shared-code model grants the same access to everyone with the code. The processing employee's name is a manually entered field rather than a verified user identity.
